## Experiment 1: synchronous active tab content selection — FAILED

Hypothesis: `ScheduleActiveBrowserSync()` uses `CefPostDelayedTask(..., 0)` even though `kTabContentActivationDelayMs == 0`. Applying `ApplyActiveBrowserSelection()` synchronously might reduce tab-switch visible/first-rAF latency.

Change tested: call `ApplyActiveBrowserSelection(generation)` directly when delay <= 0.

## Safety incident response: coredump storm guard

User reported a postmortem showing prior vimbrowser benchmark/xenv crash storms caused systemd-coredump to temporarily consume huge disk space, producing ENOSPC elsewhere. Current disk recovered (~211G free); `/var/lib/systemd/coredump` ~4.1G; no active benchmark processes.

Applied guard: benchmark harness now launches browser sessions with `ulimit -c 0 || true; exec ./vimbrowser ...`, so browser/renderer subprocesses inherit RLIMIT_CORE=0. This prevents future benchmark crash storms from writing giant systemd core dumps.

Policy going forward: keep generated experiment data under ~100GB; use `/tmp` for benchmark temp roots; run custom crash-prone vimbrowser/xenv launches with `ulimit -c 0` as well.
