## Safety incident response: coredump storm guard

User reported a postmortem showing prior vimbrowser benchmark/xenv crash storms caused systemd-coredump to temporarily consume huge disk space, producing ENOSPC elsewhere. Current disk recovered (~211G free); `/var/lib/systemd/coredump` ~4.1G; no active benchmark processes.

Applied guard: benchmark harness now launches browser sessions with `ulimit -c 0 || true; exec ./vimbrowser ...`, so browser/renderer subprocesses inherit RLIMIT_CORE=0. This prevents future benchmark crash storms from writing giant systemd core dumps.

Policy going forward: keep generated experiment data under ~100GB; use `/tmp` for benchmark temp roots; run custom crash-prone vimbrowser/xenv launches with `ulimit -c 0` as well.

## Experiment 2: disable native network response capture on the default browsing path — SUCCESS

Hypothesis: native IPC network capture was always enabled. For every request it captured request headers/body previews, response headers, and installed a `CefResponseFilter` that copied response bytes into an in-memory string up to 1MiB per request. This is valuable for diagnostics/replay but inappropriate on the normal browsing/benchmark fast path, especially for resource-heavy pages.

Change:
- Add `NativeNetworkCaptureEnabled()`.
- Default network capture off.
- Enable diagnostics with `VIMBROWSER_NETWORK_CAPTURE=1` or `--enable-vimbrowser-network-capture`.
- Keep returning the resource handler so native content blocking still runs.
- With capture disabled, no network records are created and no response filter is installed.

Broad local repeated benchmark (3 runs) was mostly neutral/noisy:

| --- | ---: | ---: | ---: |
| local.tab_switch.visible_ms p95 | 55.82 / 55.92 | 53.97, 55.78, 55.64 | 55.13 / 55.64 |
| local.tab_switch.first_raf_ms p95 | 55.82 / 55.92 | 53.97, 55.78, 55.64 | 55.13 / 55.64 |
| local.open_page.observed_complete_ms p95 | 202.14 / 200.85 | 198.63, 206.30, 205.33 | 203.42 / 205.33 |
| startup.single.page_complete_elapsed_ms p95 | 414.72 / 412.89 | 424.79, 478.37, 425.77 | 442.98 / 425.77 |

Focused local network-heavy benchmark with 80 x 512KiB image resources, alternating capture off/on in the same script:

Live repeated smoke with YouTube/GitHub/Monkeytype remained healthy; YouTube load event improved slightly/noisily, GitHub/Monkeytype readiness improved/noisy. Because live is network-variable, the focused local resource-heavy benchmark is the main proof.

## Safety hardening: disk preflight and custom safe-run wrapper

Follow-up to the coredump/ENOSPC postmortem. Added a second guard layer so benchmark experiments fail closed before disk gets tight:

- `scripts/vimbrowser-benchmark` now checks free space before running and refuses to start by default unless the repo filesystem has at least 100GiB free and `/tmp` has at least 1GiB free.
- Added `scripts/vimbrowser-safe-run` for custom/non-harness xenv experiments. It performs the same disk preflight and runs the command with `ulimit -c 0`.

This keeps the normal benchmark harness and future ad-hoc vimbrowser experiments aligned with the ~100GB maximum generated-data safety budget.
